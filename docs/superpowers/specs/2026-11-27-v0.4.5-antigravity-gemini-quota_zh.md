## 0. 结论

**可行，按「只做 Gemini Models 分组」收窄后，v0.4.5 的 Antigravity 接入变成一次「零 schema 变更、零视图改动」的新增 provider 工作。**

四点依据：

1. `gemini-weekly` 是本账号唯一同时具备「百分比 + 重置时间」的桶，另外两个 3p 桶的 `resetTime` **未提供**（键不存在）。
2. 单窗口是这套代码里已经跑通的形态（智谱 GLM 就只返回一个窗口），英雄区/副行/Console 都无需改动。
3. 收窄使三个原计划项自动消失：`QuotaWindowSnapshot` 加 `groupName`、英雄区双窗口二义、「未提供」重置时间的 UI 形态。
4. 真正的工程难点不在解码，而在**凭据形态**——`BalanceRefreshController` 在凭据为空时直接短路成 `.notConfigured`，所以必须先用一个装饰器把 daemon 文件「翻译」成非空凭据。

## 2. 边界范围

### 2.1 本版做

| 项 | 内容 |
|---|---|
| 数据分组 | **仅 `Gemini Models` 分组**；实现上遍历该分组下**全部**桶，不硬编码 `bucketId == "gemini-weekly"` |
| 取数字段 | `remainingFraction`、`resetTime` |
| 取数路径 | ① `~/.gemini/antigravity/daemon/hub_*.json` 优先；② `lsof -nP -iTCP -sTCP:LISTEN -F pcn` 按 pid 分组探测兜底 |
| 失败分级 | 401/403 = 在跑未登录；连接被拒 = 未运行 |
| 供应商形态 | 新增 `ProviderID.antigravity`，`detailKind: .quotaUsage`，`credentialManagement: .localExternalConfiguration` |

**为什么是「分组下全部桶」而不是「`gemini-weekly` 这一个桶」：**

- 本账号实测该分组只有 1 个桶，两种写法等价；
- 付费 Pro 账号的 Gemini 分组会多出 `gemini-5h`，按分组遍历可**不改代码**覆盖；
- 硬编码 bucket id 更脆（上游改 id 即失效）。

### 2.2 本版不做（含延后项的触发条件）

| 延后项 | 为什么不进 v0.4.5 | 重新启动的触发条件 |
|---|---|---|
| **`Claude and GPT models` 分组**（`3p-weekly` / `3p-5h`） | 两个桶的 `resetTime` **未提供**；且当前值都是 `remainingFraction: 1`（100%），信息量为零，只会多两行空白 | 上游开始返回 3p 的 `resetTime`；或用户反馈需要第三方面额度的可见性 |
| **模型目录**（13 个模型 + `New`/`Leaving Soon`/`Notice`/`Paid Pro`） | 数据在**另一个 RPC**（`GetCascadeModelConfigData`），既不是金额也不是百分比；应照 `CodexManualResetCreditsProvider` 做成**并行子系统**，工作量约为额度接入的 2 倍 | 额度接入稳定后，单独开 issue |
| **agy CLI 兜底** | 实测三个独立问题：`1970-01-01T00:00:00Z` 哨兵、单次 9–14 秒、每次调用残留一个 `agy` 进程 | 需要「Antigravity 未运行时仍能取数」时 |
| **`remainingFraction` 缺失时的策略** | 本账号三个桶都带该字段，**未触发**；三种候选（抛错 / 视为 0% / 视为 100%）需在真正遇到时定 | 接入 3p 或遇到缺失字段时 |
| **英雄区「最紧张窗口」语义** | 单窗口时无意义；且它会改所有 `quotaUsage` provider 的共性行为，属独立一步 | 出现需要同时显示多个窗口的场景 |
| **`QuotaWindowSnapshot` 加 `groupName`** | 见 2.3 | 同「3p 分组」 |
| 发布动作（bump 版本、打包、tag） | 本文件只到实现与验收 | 发布阶段另行执行 runbook |

### 2.3 收窄后哪些原计划项不再需要

| 原计划项 | 为什么现在不做 | 依据 |
|---|---|---|
| `QuotaWindowSnapshot` 增加 `groupName` 字段 | 只剩一个分组、一个窗口，平铺的一维 `windows` 数组已足够表达 | 实测该分组仅 1 个桶；且 `ZhipuCodingPlanProvider.swift:73` 已用 `windows: [window]` 单窗口形态跑通，`ZhipuCodingPlanProviderTests.swift:91` 断言 `windows.count == 1` |
| 英雄区「5 小时优先 vs 最紧张窗口」二义 | 单窗口时两者等价，不构成歧义 | `MenuBarBalanceViewModel.swift:214-231`：`secondaryQuotaWindowSummary` 在 `secondary.isEmpty` 时返回 `nil`，副行根本不渲染 |
| 「未提供重置时间」的 UI 形态（留空 / 写「未提供」） | `gemini-weekly` 的 `resetTime` 有真实值 | 实测 `resetTime = "2026-12-03T15:13:43Z"` |

**另有一条必须记录的正确性缺口（可接受）：**

若 Gemini 分组用尽（0%）而 3p 分组仍有额度，v0.4.5 会显示「计划已用尽」，而 Antigravity 界面显示部分可用。原因是 `ProviderStatusFormatter` 读 `usage.isAvailable`，而 v0.4.5 的 `usage` 里只有 Gemini 窗口。该缺口在 3p 接入时自然消失；当前 3p 为 100%，不构成阻塞。

**这一步必须解决的架构问题（关键）：**

`BalanceRefreshController.performRefresh` 在凭据为空时**先短路**，provider 根本不会被调用：

```swift
// Sources/APIInquiryCore/Refresh/BalanceRefreshController.swift
guard let apiKey = try credentialStore.credential(forAccount: credentialAccount),
      !apiKey.isEmpty else {
    state = .notConfigured
    return
}
```

`isCredentialConfigured`（`MultiProviderBalanceCoordinator.swift:105-115`）走同一条判断。因此**只写 provider 是不够的**：Console 会显示「未配置」，刷新永不发生。

解决方式照抄 Codex 的既有做法（`CodexCredentialStore` 从 `~/.codex/auth.json` 合成凭据）：S1 同时产出**凭据载荷的编码/解码**，让装饰器把「端口 + 令牌」编码成一个非空字符串交给 `fetchSnapshot(apiKey:)`。载荷形态：

```
{"httpPort":<int>,"csrfToken":"<32-36 字符>","pid":<int>}
```

> **安全：** 该载荷含 CSRF 令牌，**不得打印、不得落盘、不得进测试夹具的真实值**。夹具一律用假令牌。令牌每次 Antigravity 重启都会变（实测文件随进程生命周期重建），所以只在内存中逐次读取，不缓存。

### S2 — lsof 兜底探测（纯 Core）

| 项 | 内容 |
|---|---|
| **编号** | S2 |
| **内容** | daemon 文件缺失时的兜底：`lsof -nP -iTCP -sTCP:LISTEN -F pcn` → 按 `pid` 分组 → **组内端口降序** → 逐个探测直到某个端口对 `RetrieveUserQuotaSummary` 返回 200。明文 HTTP 优先于 TLS（RPC 监听器通常后绑定，端口号更大） |
| **改动文件** | 修改 `Sources/APIInquiryCore/Providers/AntigravityLocalSession.swift`（加 `lsof` 分支）；新增解析器的单元测试 |
| **独立验收** | ① 解析器用**录制的 lsof 文本夹具**（`p<pid>` / `c<cmd>` / `n<addr>` 三类行）断言分组与排序正确；② 真实 `lsof` 输出各跑一次，断言不崩、返回端口列表非负；③ **负向**：给一个不含 Antigravity 进程的 lsof 输出 → 断言返回空列表并落到 `appNotRunning` |
| **影响面** | 仍是 S1 的新文件；不动既有代码 |
| **依赖** | S1 |
| **回滚** | 移除 `lsof` 分支，退回纯 daemon 读取（功能降级但不崩） |
| **碰 UI 层？** | **否** |

**实测依据：**

```
$ lsof -nP -iTCP -sTCP:LISTEN -F pcn | head -6
p674
crapportd
f11
n*:56329
f12
n*:56329
```

格式为每进程 `p<pid>` + `c<命令名>`，其后每 socket 一组 `f<fd>` + `n<地址>`。解析时需跳过 `f` 行、只取 `n` 行末段端口。

**为什么组内降序：** 实测 Antigravity 的 `httpsPort = 63421` / `httpPort = 63422`，agy 的 `53870` / `53871` —— 明文 RPC 端口号都更大。降序能先命中明文端口，避免把明文请求打到 TLS 监听器上。

**为什么在 provider 内做 `"weekly"` → `"Week"`，而不改 `QuotaWindowKind(label:)`：**

现有映射只认 `"5h"/"Week"/"7d"/"Month"/"Monthly"/"1M"`：

```swift
// Sources/APIInquiryCore/Models/BalanceModels.swift
public init?(label: String) {
    switch label {
    case "5h": self = .fiveHour
    case "Week", "7d": self = .week
    case "Month", "Monthly", "1M": self = .month
    default: return nil
    }
}
```

接口下发的是 `"weekly"`（小写），**不在表内**，直接透传会导致中文界面出现英文 `weekly`。但 `QuotaWindowKind(label:)` 被 Codex 的 `"Week"` 依赖，改它属于共性变更。按「小步叠加」，**在 provider 内一次性转成规范标签**，不动共享映射。

**`resetAt` 的实测形态：**

| 桶 | `resetTime` |
|---|---|
| `gemini-weekly` | `"2026-12-03T15:13:43Z"` |
| `3p-weekly` | **未提供**（键不存在） |
| `3p-5h` | **未提供**（键不存在） |

由于只取 Gemini 分组，v0.4.5 的 `resetAt` 恒非空，不需要处理「未提供」。


- S2 依赖 S1（复用同一文件与错误类型）。
- S3 依赖 S1（需要 session 载荷），**不依赖 S2**——daemon 文件能读到就不需要 lsof。
- **S2 可以先不合入**：只要 S1 + S3 + S4 齐备就能跑通本账号的 happy path。S2 是健壮性增量，可单独排在 S4 之后合入而不阻塞 S5。

### 4.1 为什么 Gemini 分组本身即可支撑第一版

| 维度 | Gemini 分组给的 | 是否够用 |
|---|---|---|
| 主数字 | `0.5508368` → `55%` 剩余 | 面板与菜单栏的核心诉求 |
| 重置时间 | `2026-12-03T15:13:43Z` → `12/03` | 真实日期，不是哨兵 |
| 可用性判定 | `remainingPercentage > 0` → 计划可用 | 状态行可用 |
| 菜单栏标题 | `.week` → 纯百分比 | 已有路径 |

**一个桶就把「还能用多久、什么时候回血」两件事都答了。** 这正是面板存在的理由。反面：3p 分组当前是 `100% / 100%`，且 `resetTime` **未提供**，加进来只会多两行空白，不增加任何决策价值。

### 4.2 为什么 3p 延后不阻塞后续演进

| 保证 | 说明 |
|---|---|
| 传输层不用重写 | S1/S2 产出的是 session（端口 + 令牌），与「解几个桶」无关。后续加 3p 只改 S3 的分类过滤那一段 |
| 那时才需要 `groupName`，现在不加正好 | `QuotaWindowSnapshot` 加可选字段是纯增量（默认 `nil` 自动兼容 `Equatable`），留到真正需要二维表达时再加，避免预埋当前用不到的扩展点 |
| 模型目录完全正交 | 它是并行子系统（类比 `CodexManualResetCreditsProvider`），不碰 `QuotaUsageSnapshot`，可独立排在更后的版本 |

## 5. 风险与对策

### 5.1 旧 daemon 文件残留

| | |
|---|---|
| **现象** | Antigravity 崩溃或被强杀后，`hub_*.json` 可能留在磁盘上，但端口已关闭 |
| **实测依据** | 正常退出时目录被清空：`~/.gemini/antigravity/daemon/` 于 `Nov 27 16:49:07` 变为空目录。连已关闭端口返回 `curl: (7) Failed to connect to 127.0.0.1 port 63499` |
| **对策** | ① 读文件后校验 `pid` 存活（`kill(pid, 0)`）；② 校验 `lsVersion` 与期望值兼容；③ 连不上时**不报「未配置」**，报 `appNotRunning`；④ 多个 `hub_*.json` 时取 mtime 最新且 pid 存活的那个 |

### 5.2 端口探测误选

| | |
|---|---|
| **现象** | 多产品并存（App + IDE + agy）时，可能把明文 JSON 请求打到 TLS 监听器上 |
| **实测依据** | 明文端口打到 TLS 监听器返回 `Client sent an HTTP request to an HTTPS server.` + `HTTP 400`；agy 上无令牌的 RPC 返回 `HTTP 401` |
| **对策** | ① 按 `pid` 分组、**组内端口降序**（实测 http 端口号恒大于 https）；② 每个候选都实际探一次 `GetUserStatus` 或 `RetrieveUserQuotaSummary`，只接受 200；③ 全部失败时按 ai-usagebar 的教训**优先报「在跑但未登录」**，因为那是用户能动的，连接拒绝只说明没开 |

### 5.3 权限与令牌过期

| | |
|---|---|
| **现象** | daemon 文件是 `0600` 用户私有；CSRF 令牌随进程重建而变 |
| **实测依据** | `stat` → `-rw-------`，`csrfToken` 长度 36；不带令牌的请求返回 `{"code":"unauthenticated","message":"unauthenticated: missing CSRF token"}` `HTTP 401` |
| **对策** | ① 每次刷新都重新读文件，**不缓存令牌**；② 401/403 映射为「在跑但未登录」并给重试动作，不提示「替换 Key」（本 provider 没有 Key 可换）；③ App 未做沙盒（`codesign -d --entitlements - "/Applications/API Inquiry.app"` 无 `app-sandbox` 条目），读 `~/.gemini` 不需要额外权限；④ 令牌只进内存，**不打印、不落盘、不进夹具** |

### 5.4 其他

| 风险 | 对策 |
|---|---|
| 私有 RPC 随 Antigravity 版本变更 | 记录 `lsVersion` 到错误文案；RPC 返回 404/非 JSON 时归类为 `versionChanged`，提示「Antigravity 已升级」而不是「未配置」 |
| 桶数量不固定 | 按分组遍历，**不假设**存在 `gemini-5h`；空分组直接 `missingBalanceInfo` |
| 付费账号多出 `gemini-5h` 后双窗口 | 英雄区按既有规则取第一个 `.fiveHour`，行为自动成立；S5 用 `--fixtures` 补看一次 |
| 既有 5 个 provider 回归 | 每步合入前必须确认它们的快照字段未变（见 §6） |
