# API Inquiry v0.3.14 Codex Menubar 额度精简设计

## 概要

v0.3.14 精简 OpenAI/Codex 额度供应商的 Menubar 展示。Menubar 只显示一个剩余百分比，例如 `72%`，不再包含 `5H 72%` 或 `1W 48%` 这类额度窗口标签。

额度选择仍沿用现有优先级：有 5 小时窗口时显示 5 小时额度；没有 5 小时窗口时显示可用的周额度。打开 Menubar 详情后，仍完整展示接口返回的每个额度窗口，包括本地化标签、剩余百分比、重置时间、可用状态和颜色状态。

在当前供应商注册表中，用户可见的 OpenAI 次级名称对应 `.codex` 供应商及 `CodexQuotaProvider`。

## 目标

- 从 `main` 创建隔离的 `v0.3.14` 分支开展本次工作。
- Codex 作为 Primary Provider 时，Menubar 仅显示 `xx%`。
- 同时存在 5 小时和周窗口时，优先显示 5 小时额度。
- 接口没有返回 5 小时窗口时，回退显示周额度。
- 双窗口和单窗口响应在点击后的 Menubar 详情中都保持完整。
- 保持 DeepSeek、智谱 GLM Coding Plan、Codex 手动重置额度及所有非 Menubar 表面的现有行为。
- 用自动化测试覆盖格式化边界和从供应商到 Menubar 的完整数据流。

## 非目标

- 不修改 Codex 接口、凭证流程或响应结构。
- 不修改 `used_percent`、重置时间或窗口时长的解析方式。
- 不重新设计 Menubar 详情或 Console。
- 不修改本地化详情标签、状态文案、数值颜色或重置时间格式。
- 不为供应商新增通用、可配置的 Menubar 展示策略。
- 本次行为优化不包含发布打包、打 tag 或发布操作。

## 展示契约

| 返回的已识别窗口 | Menubar 展示 | 点击后的 Menubar 详情 |
| --- | --- | --- |
| 5 小时和周窗口 | 5 小时剩余百分比，例如 `72%` | 一个 5 小时行和一个周额度行 |
| 仅 5 小时窗口 | 5 小时剩余百分比，例如 `72%` | 一个 5 小时行 |
| 仅周窗口 | 周额度剩余百分比，例如 `48%` | 一个周额度行 |
| 没有已识别的可用窗口 | 沿用现有不可用或错误展示 | 沿用现有不可用或错误展示 |

Menubar 不标明百分比来自哪个已识别窗口，窗口上下文由详情行提供。

百分比沿用现有格式化规则：显示前截取为整数。例如 `72.9` 显示为 `72%`。

## 设计

### 窗口选择

`ProviderValueFormatter.primaryQuotaWindow(in:)` 继续作为窗口选择边界：

1. 优先选择语义类型为 `.fiveHour` 的第一个窗口。
2. 不存在 5 小时窗口时，选择供应商保留下来的第一个已识别窗口。

`CodexQuotaProvider` 根据 `limit_window_seconds` 判断窗口语义，而不是根据响应字段名 `primary_window` 或 `secondary_window` 判断。它保留已识别的 5 小时和周窗口，只有在一个已识别窗口都没有时才拒绝响应。因此，604,800 秒的 `primary_window` 加 `secondary_window: null` 这类仅周额度响应是有效输入。

### Menubar 格式化

`ProviderValueFormatter.menuQuotaWindowText(for:)` 继续作为 `menuValueText` 使用的紧凑额度格式化入口。

对于已识别的 `.fiveHour` 和 `.week` 窗口，它只返回格式化后的剩余百分比。对于防御性保留的未知窗口，继续使用现有的 `标签 xx%` 形式，避免未来的意外值在失去上下文后展示。

`MenuBarBalanceViewModel.menuBarValueText` 和 `menuBarTitle` 继续直接使用格式化结果。Codex 不增加供应商文字前缀。

### 点击后的 Menubar 详情

详情渲染路径不做修改。

`MenuBarBalanceViewModel.primaryQuotaWindowRows` 继续映射 `QuotaUsageSnapshot.windows` 中的全部窗口。每个详情行保留：

- 本地化的 5 小时或周额度标签。
- 剩余百分比和数值颜色。
- 剩余额度后缀。
- 重置时间或重置日期。
- 可用状态。

接口返回两个已识别窗口时显示两行；仅返回周窗口时只显示一行周额度。次级供应商的额度详情行也继续保持完整。

### 其他展示表面

`detailText`、`secondaryDetailText`、`consoleDetailText` 和 `primaryDisplayParts` 均不修改。因此，DeepSeek 现金余额、智谱计划用量、Console 摘要和 Codex 手动重置额度维持现有输出。

## 数据流

1. `CodexQuotaProvider` 将已识别额度窗口解析到 `QuotaUsageSnapshot.windows`。
2. `BalanceRefreshController` 和 `MultiProviderBalanceCoordinator` 发布已加载快照。
3. `MenuBarBalanceViewModel.menuBarValueText` 请求紧凑展示值。
4. 格式化器优先选择 5 小时窗口，否则选择周窗口，并只输出 `xx%`。
5. 用户打开 Menubar 后，`primaryQuotaWindowRows` 独立地将所有已返回窗口映射为详情行。

紧凑 Menubar 数值与详细窗口行有意使用相互独立的展示路径。

## 错误处理

现有状态和供应商错误处理保持不变：

- 未配置状态继续显示 `Setup` 或对应本地化文案。
- 没有历史快照的加载状态继续显示 `--`。
- 带历史快照的加载或失败状态继续沿用现有历史快照行为。
- 鉴权、限流、服务端、解码和额度缺失错误继续使用现有映射。
- 未知窗口时长继续由供应商过滤。

不新增用户可见文案或本地化键。

## 测试

使用自定义 `APIInquiryCoreTestsRunner`，只使用假凭证和模拟 HTTP。

- 双窗口 Codex 快照在 `menuBarValueText` 和 `menuBarTitle` 中都输出 `72%`，数值取自 5 小时窗口。
- 同一双窗口快照仍暴露两条详情行，保留 5 小时和周额度的标签、数值与重置文案。
- 仅周窗口快照输出周额度剩余百分比，不包含 `1W`、`7d` 或 `Week` 前缀。
- 仅周窗口 HTTP 响应经过 `CodexQuotaProvider`、刷新控制器、协调器和 Menubar ViewModel 后，仍暴露一条周额度详情行。
- 中文和英文的 Menubar 都只显示百分比，详情标签继续按语言本地化。
- DeepSeek 和智谱的 Menubar 断言保持不变。
- 空值、加载、失败和未配置状态维持现有行为。

手工验收前运行完整自定义测试 Runner 和 `swift build`。

- Codex 双窗口响应在 Menubar 中以 `xx%` 显示 5 小时剩余额度。
- Codex 仅周窗口响应在 Menubar 中以 `xx%` 显示周剩余额度。
- 点击后的 Menubar 详情准确展示查询返回的全部已识别窗口。
- 其他供应商及相邻 Codex 展示表面不发生变化。
- 完整自定义测试 Runner 和构建通过。

## 本地 UI 验收包不变量

首个 v0.3.14 本地验收包在 SwiftUI 源码完全未改动的情况下出现了仅由构建造成的视觉回归。已安装的 v0.3.12 应用链接 macOS 26.5 SDK，而本地验收包继承了 `SDKROOT=MacOSX15.4.sdk`。详情面板使用系统提供的 `MenuBarExtra` window 样式，因此旧 linked SDK 选择了旧版的不透明表面和更小圆角，而没有采用当前 macOS 的原生材质。

本地构建还把一个由 SwiftPM 签名的可执行文件复制进未完成整体签名的 app wrapper。它的 `Info.plist` 没有绑定到签名，严格 bundle 验证失败，同一产物中的 `SMAppService.mainApp.status` 也表现为不可用。无效 bundle 身份是该状态目前最有力的解释，而且无论如何都不可接受；但仅凭截图还不能证明它是唯一可能原因。这是本地验收产物缺陷，不是额度格式化或 SwiftUI 源码改动。

因此，本地 UI 验收增加以下不变量：

- `Scripts/build-local-app.sh` 必须显式解析当前活跃的 macOS SDK，不能继承通用的测试专用 `SDKROOT`。
- 只有项目专用的 `API_INQUIRY_APP_SDKROOT` 才能用于有意选择其他应用 SDK。
- 应用必须先在干净的 `/private/tmp` staging 目录中完成组装和 ad-hoc 签名，再复制到 `.build/APIInquiry.app`。
- staging 中的应用和复制后的应用都必须通过 `codesign --verify --deep --strict`。
- 本地应用元数据应与发布 bundle 中影响应用身份和正常 macOS 展示的字段保持一致。
- UI 验收必须检查构建产物的 `LC_BUILD_VERSION`、bundle 签名和真实面板外观；只检查源码 diff 不足以证明 UI 未变化。

修复不得新增自定义面板背景、圆角或透明效果。目标外观仍由链接当前 SDK 后的 `.menuBarExtraStyle(.window)` 原生提供。
