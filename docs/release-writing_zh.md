# 发布文案怎么写

发布时有三种文字，读者不同，写法也不同：

| 文本 | 读者 | 回答的问题 |
|---|---|---|
| Release Notes（`docs/releases/vX.Y.Z_github.md`） | 用这个 App 的人 | 这一版对我有什么变化？ |
| CHANGELOG（`CHANGELOG.md` / `CHANGELOG_zh.md`） | 想追溯历史的人、贡献者 | 哪个版本改了什么？ |
| `docs/releases/vX.Y.Z.md` / `_zh.md` | 同上，但只含单一语言 | 同上 |

同一件事在三处可以写三遍，但**详略必须不同**：Release Notes 只写感知，CHANGELOG 记录事实与数字。

## Release Notes

### 结构

只有三节，没有内容就整节省略：

- 新增功能
- 应用优化
- 问题修复

每条一行：加粗短语概括变化，后面一句话解释对用户意味着什么。

### 只写"看得见的变化"

判断标准：用户升级后，会不会在界面上注意到？会不会改变他的操作？

```
✅ 面板更紧凑：主区只保留当前窗口，其余窗口收成一行摘要。
❌ 面板高度由 442pt 收紧到 364pt。
```

第二种写法是给开发者看的，属于 CHANGELOG。

### 不要写

- 具体数字（18%、442pt、39pt 列宽）—— 放进 CHANGELOG
- 文件名、内部类型名、框架名
- 测试数量、构建参数
- "重构了……""统一了……"这类工程叙述
- 纯文档、许可证、CI、脚本改动（用户不会感知）
- 对旧行为的抱怨式解释（"不再是……"写一次就够，不要反复强调）

### 语气

陈述句，短句，不夸张，不用"革命性""大幅提升"。用户读 Release Notes 的时间通常是十秒。

### 数量

- 新增功能 3–6 条
- 应用优化 3–8 条
- 问题修复 2–6 条

超过这个量，通常说明这个版本太大，或者把内部改动写进来了。

## CHANGELOG

沿用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 与 SemVer：

- 版本新的在上，标题 `## [x.y.z] - YYYY-MM-DD`
- 小节对应关系：Added → 新增功能，Changed → 应用优化，Fixed → 问题修复，Removed → 移除
- **这里可以也应该写技术细节**：数字、内部重构、文档与工具链改动
- 每条一行；能追到 issue/PR 就带编号，例如 `(#80)`
- 中英两份镜像：版本标题、小节顺序、条目数量必须一致
- 发布当天把 `[Unreleased]` 折叠成新版本小节并填日期，`[Unreleased]` 留空

## 判断一条变动放哪儿

依次问三个问题：

1. **用户会注意到吗？** 不会 → 只进 CHANGELOG（甚至只进 commit）
2. **能用用户的语言一句话说清吗？** 能 → Release Notes 写一句，CHANGELOG 记细节
3. **它改变的是行为还是实现？** 行为 → Release Notes；实现 → CHANGELOG

## 实例：v0.4.0 的改写

| 最初写的 | 最终 Release Notes | CHANGELOG |
|---|---|---|
| 面板高度减少约 18% | 面板高度也做了优化 | 442pt → 364pt |
| 列宽随内容自动收缩，不再固定预留 | （不写） | 典型值 39 / 48 / 65pt |
| 四个字标按同一视觉基准缩放 | 各家 logo 大小终于一致 | 按字面高度基准缩放 |

观察规律：**Release Notes 里删掉的数字，全部在 CHANGELOG 里补回来**，没有信息丢失，只是换了读者。

## 清单

```
[ ] Release Notes 只有新增功能 / 应用优化 / 问题修复三节，空节省略
[ ] 每条以加粗短语开头，一句话解释用户感受
[ ] 没有数字、文件名、类型名、测试数、框架名、重构措辞
[ ] 文档 / 许可证 / CI / 脚本改动没有出现在 Notes 里
[ ] CHANGELOG 折叠了 Unreleased，日期与发布日一致
[ ] 中英两份版本标题、小节、条目数一致
[ ] 从 Notes 删掉的数字，在 CHANGELOG 里找得到
```
